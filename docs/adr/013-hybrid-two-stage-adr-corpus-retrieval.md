# ADR 013: ADRコーパス肥大化に対するハイブリッド2段階検索方式の導入

* **ステータス:** Accepted
* **日付:** 2026-08-10

## 1. 背景と目的 (Context & Objective)

ある時点で、本ツールを導入しているある商用プロダクションリポジトリ（以下「導入先リポジトリA」）の PR で `enforce-adr` チェックが `Error: ADR documents size exceeds the maximum limit` で失敗した。

1. **原因**: `src/utils/adrLoader.ts` の `loadAdrFiles` は、`docs/adr` 配下の全 `.md` ファイルを無条件に結合し、`LlmJudge.evaluate` の System Prompt（`<adr_documents>...</adr_documents>`）にそのまま丸ごと埋め込んでいる。ADR-011 で導入した `MAX_ADR_SIZE = 100,000`（文字数）は、当時のADR数（12件程度）を前提にした安全な上限値だったが、導入先リポジトリAのADRコーパスは70件超・**28万文字超**まで増加しており、上限を約3倍超過していた（具体的な件数・文字数は導入先の実装規模に関する情報のため、本ADRでは概数のみ記載する）。
2. **単純な上限引き上げでは根本解決にならない**: `MAX_ADR_SIZE` を引き上げても、ADRは今後も増え続ける前提（本ツール自体の目的がADRドキュメントの継続的な蓄積を促すことである）のため、いずれ再び上限に到達する。
3. **「全文を毎回投げ込む」設計自体に、精度上のリスクがある（Lost in the Middle）**: ADR-011 は本リスクを「トークン枯渇」の観点からのみハードリミットで防御していたが、2026年時点のLLM運用のベストプラクティスでは、無関係な文書を大量に含む長大なコンテキストは、モデルの注意が分散し、コンテキスト中盤の情報を見落とす「Lost in the Middle」現象により、**関連文書のみに絞り込んだ場合よりもかえって判定精度が下がる**ことが複数の実証研究で示されている。すなわち、単純な上限引き上げは「Fail-Closedの発生を遅らせるだけ」であるだけでなく、「限度内に収まっている場合でも、ノイズになる無関係なADRが判定精度を下げている」可能性がある。
4. **一方で、素朴な検索（Naive Vector RAG等）への全面移行も推奨されない**: 関連文書の取りこぼし（Retrieval Miss）は、本ツールが最も避けるべき「ADR違反の見逃し」に直結するため、単純な類似度検索だけに判定を委ねることはできない。

2026年時点のLLMアプリケーション設計の標準的な指針は、「全文投げ込み」でも「素朴なRAG」でもなく、**「軽量なインデックスで関連範囲を絞り込んでから、その範囲内でロングコンテキスト推論を行うハイブリッド方式」**である。

## 2. 決定事項 (Decision)

`loadAdrFiles` による無条件の全文結合を廃止し、以下の**「ハイブリッド2段階ADR検索」**を導入する。

### 2.1. Stage 1: 軽量インデックスによる関連ADRの絞り込み

* 各ADRファイルは、既存の運用慣行として frontmatter に `title` と `description`（そのADRが扱う課題・決定の要約）を持つ想定とする（導入先リポジトリAでは全ADRに一貫して付与されている運用実績がある）。これを`docs/adr`の各ファイルから軽量に抽出し、`{ファイル名, title, description}` の一覧（既存の`combinedContent`とは別の軽量コーパス）を構築する。
* この一覧とPR Diffを`LlmJudge`とは別の軽量な先行LLM呼び出し（もしくは同一`evaluate`呼び出し内の最初のステップ）に渡し、「このDiffに関連しそうなADRファイル名」を判定・列挙させる（Summarization First、ADR-012の巨大PR監査で既に採用している手法と同じ設計思想）。

### 2.2. Stage 2: 絞り込んだADRのみ本文を渡して監査

* Stage 1で列挙されたADRファイルのみ、`loadAdrFiles`相当の処理でフル本文を読み込み、これまで通り`LlmJudge.evaluate`の`<adr_documents>`へ埋め込んで最終判定を行う。
* **安全側マージン**: Stage 1の絞り込み結果に対しても`MAX_ADR_SIZE`（ADR-011）を引き続き適用する。絞り込んだ後もなお上限を超える場合は、境界サイズを是正できないため、これまで通りFail-Closedとする（`fail_open: false`の設計思想を維持）。
* **取りこぼし対策**: Stage 1のプロンプトでは、「該当しそうなADRの選定は広めに（false negativeよりfalse positiveを許容する）行うこと」を明示的に指示し、素朴な類似度ベースRAGで指摘されている「関連文書の取りこぼし」リスクを、LLM自身による意味的な広めの絞り込みで緩和する。

### 2.3. 既存の`MAX_ADR_SIZE`ハードリミット（ADR-011）は撤廃しない

* Stage 1のインデックス自体、および「Stage 1がすべてのADRを関連ありと判定してしまった場合」の両方に対する最終防衛線として、`MAX_ADR_SIZE`は維持する。これにより、本対応はADR-011の代替ではなく、ADR-011の上に成立する追加の防衛層として位置づける。

## 3. もたらされる結果 (Consequences)

* **【ポジティブ】** ADRコーパスがどれだけ増えても（導入先リポジトリAのように今後も継続的に増加する前提でも）、`MAX_ADR_SIZE`の固定上限に構造的に到達しにくくなる。
* **【ポジティブ】** 無関係なADRをコンテキストに含めなくなることで、Lost in the Middle由来の判定精度低下リスクが軽減され、ADR違反検知の精度向上が期待できる。
* **【ポジティブ】** Stage 1のインデックス自体は軽量（数千文字程度）なため、既存の`MAX_ADR_SIZE`のような対応が別途必要になることは当面考えにくい。
* **【ネガティブ】** LLM呼び出しが1段階から2段階に増えるため、レイテンシとAPIコストがわずかに増加する。ただしStage 1は軽量なインデックスのみを扱うため、増加分は限定的である。
* **【ネガティブ】** Stage 1の絞り込みロジック自体がLLMの判断に依存するため、理論上は「本来関連するはずのADRを見落とす」リスクをゼロにはできない（2.2の安全側マージンで緩和するのみ）。
* **【ネガティブ／前提条件】** 本対応は、利用先リポジトリの各ADRファイルが frontmatterに意味のある`description`を持っていることを前提とする。`description`が空、または存在しないADRファイルが混在する場合、Stage 1の絞り込み精度が低下する。導入先リポジトリAは既に全ADRに`description`を付与済みだが、他の利用先リポジトリへの適用時は同様の運用慣行が前提条件になることを明記する。
